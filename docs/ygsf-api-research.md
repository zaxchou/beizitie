# 以观书法 API 规律调研（第一性原理）

> 目的：彻底搞清以观书法（ygsf）字库 API 的数据行为，为背字帖字库的可靠导入/修复提供依据。
> 本文所有结论均来自 2026-09-04 的受控实验，实验脚本：`server/scripts/ygsf-research-windows.ts`，原始日志：服务器 `/opt/zi2anki/research-log.txt`。
> 状态：**研究进行中** — 本文档随实验更新，结论未定前不动生产数据。

---

## 1. 背景

用户报告敦煌遗书佛说父母恩重经字图不符。排查发现这不是我们的导入代码 bug，而是以观 API 的数据行为问题。此前一轮批量"修复"误判数据损坏范围，已全部回滚（生产库与事故前一致：2852 帖/上架 2707/172.6 万卡）。

## 2. 两个数据端点

| 端点 | 行为 |
|---|---|
| `zitie/glyphs/query?zid&loaded=N` | 按偏移翻页（120/页）。有完整 `total`。 |
| `zitie/page/glyphs?zid&page=N` | 按页取（通常 page=1 一次返回全量）。**部分帖只返回很小的子集**（九成宫 2 条、东比帖 8 条），覆盖率因帖而异。 |

两端的 `_id` 集合一致（同一份字形库），`_id` 与图片 CDN 文件名的对应关系因帖而异（部分帖 `_id == 文件名`，部分帖不是）— **因此卡片对齐一律用图片文件名，不用 `_id`**。

## 3. 已验证的规律（受控实验）

### 3.1 `_id` 与图片 URL 稳定（H1 ✅）
同一 zid 多次请求，`_id` 序列指纹完全恒定。图片 URL 由 `_id`/文件名决定，也稳定。**图片是可靠的，会漂移的只有 `_hanzi` 标签。**

### 3.2 标签按"时间窗"在多状态间切换（H2 ✅）
- 同一 zid 的响应存在 **N 种标签状态**（实验中一帖 4 轮出现 3 种状态）。
- `_id`→标签 的配对整体切换，**不是逐条随机**。
- 其中恰好一个状态是**真值态**（标签连起来就是碑帖原文，如"佛說父母恩重經如是我聞…"），其余为**垃圾态**（随机汉字）。

### 3.3 垃圾态每次随机生成，真值态窗口内稳定重复（H3 ✅）
- 垃圾态：同一 id 每次拉到的标签**都不同**（双拉一致率≈0）。
- 真值态：窗口内连续多次拉取完全一致。
- **推论：连续两次拉取完全一致 ⇒ 命中真值态**（垃圾态不可能两次相同）。这是无外部真值时的可靠判据。
- 窗口持续时间：分钟级。窗口出现频率随帖而异（敦煌帖上午/中午/下午多次命中；九成宫长时间未命中）。

### 3.4 各帖窗口相互独立（H4 ✅）
并发拉 A/B 两帖，A 命中真值的同时 B 可以是垃圾态。不是全局开关。

### 3.5 两端点的状态不同步
同一轮里 query 端点真值、page 端点垃圾（或反之）是常态 — 两个端点的缓存各自独立。

### 3.6 库内数据质量（用户直觉正确 ✅）
- **绝大多数帖是好的**：九成宫醴泉铭库内头 30 字完全正确（"九成宫醴泉铭九成宫泉銘祕書監…"）。
- 少数帖在导入时赶上垃圾窗口，从某一页起整体错乱（敦煌帖前 240/971 正确，之后错；这类帖的特征是"前段正确 + 后段乱"）。

### 3.7 受控实验最终数据（2026-09-04 02:43-02:57，12 轮 × 3 帖）

| 样本 | query 真值态 | page 真值态 | 库内状态 | 备注 |
|---|---|---|---|---|
| 敦煌遗书佛说父母恩重经 | 2/12 | 2/12 | 头 240 对、后 731 错 | 真值态 = 原文序列 |
| 九成宫醴泉铭 | 1/12 | 0/12(page 多为空) | **库内全对** | 真值态 = 库内序列 |
| 永嘉马居士 | 0/12* | 0/12* | **库内全错** | *真值态频繁出现但被误标 |

- **修正性发现（永嘉马居士）**：该帖库内头部是乱字，但 API 的 stable 态返回"永嘉馬居士畣陳公虞十"（连贯文言 = 真值）。实验脚本因拿库内前缀当参照把它误标为 stable-wrong — **这证明真值判定不能依赖库内前缀，只能依赖"双拉完全一致"**（垃圾态每次随机、不可能两拉相同；真值态窗口内稳定）。
- **众数投票收敛性**：6 轮投票后，三帖均 **100% 字形拿到 ≥2 票的可信标签**（垃圾标签彼此不同永不重复，真值标签重复出现）。
- 两端点状态部分独立（同步轮数 0-8/12 不等）→ 任选一个端点做投票即可，无需两边对齐。
- 真值窗口持续时间：分钟级；出现频率因帖因时而异（0-50%）。

## 4. 防备措施（铁律）

1. **永远不用单次拉取的数据直接写库**。写库前必须满足：连续两次拉取完全一致（双拉一致判据），且头部与库内正确前缀（或原文）吻合。
2. **不删帖**。数据修复只改 `front_text`，每笔修改记录 old→new 到报告，可回滚。
3. **集字安全模式**：集字索引只收录"逐帖验证过"的帖（`jizi_verified` 表），宁可缺字不可错字。验证通过的帖逐个放行。
4. **小步推进**：1 帖 → 5 帖 → 50 帖，每步 dry-run + 抽样人工核对后才进下一步。
5. 所有核验/修复脚本必须幂等、可中断续跑、产出 JSON 报告。

## 5. 修复方案（依据上述规律设计）

`ygsf-majority-verify.ts`（多轮采样 + 众数投票，不依赖库内/原文任何先验）：
1. **采样**：每帖拉 6+ 轮（轮间间隔 1.5s+，跨越窗口切换周期）
2. **众数即真值**：同一图片文件名的标签中出现 ≥2 次的为可信真值（垃圾态标签每次随机、永不重复；真值态重复出现）；只出现 1 次的字不写、不算错
3. **比对修字**：可信真值与库内逐字比对，错配逐字修正 `front_text`，每笔修改记录 old→new 报告
4. **判定**：错配 ≤5 → OK；>5 → 修字；可信覆盖 <90% → 本轮跳过待复验

实验验证：敦煌帖 dry-run 识别 611 错字（与人工诊断一致）；永嘉马居士在修正判据后可全量修复。

## 8. 铁律（已实证，任何批量操作前必须满足）

1. **判定真值**：同一帖连续多轮拉取，某文件名的标签出现 ≥2 次才可信（垃圾标签每次随机、永不重复；真值标签重复出现）
2. **不删帖**：只改 `front_text`，每笔修改记 old→new 入报告，可回滚
3. **修后必复检**：apply 后立即 dry-run 复验，应 0 错；并抽读文字序列确认连贯可读
4. **集字宁缺勿错**：集字索引只收录 `jizi_verified` 中的帖；修一帖、放行一帖
5. **覆盖不足不动手**：可信真值覆盖 <90% 的卡 → 该帖本轮跳过，绝不"猜"
6. **批量前先小步**：1 帖 → 5 帖 → 50 帖，每步 dry-run + 人工抽查后才进下一步
7. **所有脚本幂等可续跑**，产出 JSON 报告留档
